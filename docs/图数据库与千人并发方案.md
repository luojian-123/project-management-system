# 项目管理系统 - 图数据库与千人并发技术方案

**目标**：采用图数据库作为唯一数据源，支撑约 **1000 人同时在线使用**。  
**版本**：v1.0

---

## 一、方案概述

| 项目 | 说明 |
|------|------|
| 数据层 | 仅使用图数据库（推荐 **Neo4j**），不再使用 MySQL |
| 应用层 | 保留 Spring Boot + JWT，持久层由 MyBatis 改为 Neo4j Java Driver + Cypher |
| 前端 | 不变（Vue 3 + Vite + Element Plus） |
| 并发目标 | 约 1000 人同时在线，峰值约 200～500 并发请求/秒 |
| 扩展方式 | 应用层水平扩容 + 图库连接池与资源调优，必要时图库集群 |

---

## 二、图数据模型设计

将现有业务抽象为「节点 + 关系」，便于遍历组织树、任务依赖、权限链等。

### 2.1 节点类型（Node Labels）

| 节点标签 | 说明 | 主要属性示例 |
|----------|------|----------------------|
| `User` | 用户 | id, username, realName, passwordHash, status, createdAt |
| `Company` | 公司 | id, companyCode, companyName, sortOrder |
| `Dept` | 部门 | id, deptCode, deptName, companyId, sortOrder |
| `Role` | 角色 | id, code, name, status, sortOrder |
| `Menu` | 菜单 | id, name, path, component, permission, type, sortOrder, icon |
| `Project` | 项目 | id, name, code, status, startTime, endTime, createdAt |
| `Task` | 任务 | id, name, projectId, parentTaskId, status, progress, startTime, endTime |
| `Issue` | 问题 | id, projectId, taskId, title, severity, status, createdAt |
| `Risk` | 风险 | id, projectId, description, level, probability, impact, status |
| `Cost` | 成本 | id, projectId, planAmount, actualAmount, occurDate, remark |
| `Change` | 变更 | id, projectId, changeNo, title, status, createdAt |
| `Todo` | 待办 | id, userId, title, status, dueTime, createdAt |
| `DictType` | 字典类型 | id, code, name |
| `DictItem` | 字典项 | id, typeId, itemKey, itemValue, sortOrder |

### 2.2 关系类型（Relationship Types）

| 关系 | 说明 | 方向示例 |
|------|------|----------|
| `BELONGS_TO_COMPANY` | 部门所属公司 | (Dept)-[:BELONGS_TO_COMPANY]->(Company) |
| `BELONGS_TO_DEPT` | 部门上级/角色所属部门 | (Dept)-[:BELONGS_TO_DEPT]->(Dept), (Role)-[:BELONGS_TO_DEPT]->(Dept) |
| `HAS_ROLE` | 用户拥有角色 | (User)-[:HAS_ROLE]->(Role) |
| `HAS_MENU` | 角色拥有菜单 | (Role)-[:HAS_MENU]->(Menu) |
| `PARENT_MENU` | 菜单父子 | (Menu)-[:PARENT_MENU]->(Menu) |
| `IN_PROJECT` | 任务/问题/风险/成本/变更属于项目 | (Task)-[:IN_PROJECT]->(Project) 等 |
| `DEPENDS_ON` | 任务依赖 | (Task)-[:DEPENDS_ON]->(Task) |
| `PARENT_TASK` | 任务父子 | (Task)-[:PARENT_TASK]->(Task) |
| `ASSIGNED_TO` | 任务/问题/风险分配给用户 | (Task)-[:ASSIGNED_TO]->(User) |
| `CREATED_BY` | 待办所属用户 | (Todo)-[:CREATED_BY]->(User) |
| `DICT_ITEM_OF` | 字典项属于类型 | (DictItem)-[:DICT_ITEM_OF]->(DictType) |

### 2.3 Cypher 示例（组织树、任务依赖）

```cypher
// 某公司下所有部门（一层）
MATCH (c:Company {id: $companyId})<-[:BELONGS_TO_COMPANY]-(d:Dept) RETURN d ORDER BY d.sortOrder;

// 某部门下所有角色
MATCH (d:Dept {id: $deptId})<-[:BELONGS_TO_DEPT]-(r:Role) RETURN r;

// 用户及其角色
MATCH (u:User {id: $userId})-[:HAS_ROLE]->(r:Role) RETURN r;

// 任务依赖链（某任务的所有前置）
MATCH (t:Task {id: $taskId})-[:DEPENDS_ON*]->(pre:Task) RETURN DISTINCT pre;
```

## 三、支撑 1000 人并发的架构

### 3.1 容量估算（经验值）

| 指标 | 取值 | 说明 |
|------|------|------|
| 同时在线人数 | 1000 | 同一时刻登录/使用系统的人数 |
| 峰值并发请求 | 200～500 req/s | 按 20%～50% 用户同时操作估算 |
| 单实例处理能力 | 100～300 req/s | Spring Boot 单机 + 图库查询，视接口复杂度 |
| 应用实例数 | 2～4 | 通过负载均衡分摊请求 |
| 图库连接池（每实例） | 50～100 | 与 Neo4j 的 maxConnectionPoolSize 对应 |

### 3.2 推荐拓扑

```
                    [ 用户浏览器 ]
                           |
                    [ Nginx / 负载均衡 ]
                           |
         +-----------------+-----------------+
         |                 |                 |
    [ Spring Boot ]  [ Spring Boot ]  [ Spring Boot ]   (2～4 实例)
         |                 |                 |
         +-----------------+-----------------+
                           |
                    [ Neo4j 图数据库 ]
                    (单机或因果集群)
```

- **前端**：静态资源可放 Nginx 或 CDN，与现有一致。
- **后端**：无状态，多实例 + 负载均衡；JWT 不依赖会话存储。
- **图库**：单机可支撑约 1000 人在线；若需高可用或更高吞吐，采用 Neo4j 因果集群（1 写 + 2 读副本）。

### 3.3 应用层配置（Spring Boot）

- **Tomcat 线程数**：单实例 200～500，保证足够并发处理请求。
- **Neo4j 连接池**：每实例 50～100，总连接数 &lt; Neo4j 的 `dbms.connector.bolt.thread_pool_max_size`。
- **JVM**：堆内存建议 1～2GB/实例，根据实际压测调整。

示例（`application.yml` 片段，需配合 Neo4j 驱动使用）：

```yaml
server:
  port: 8080
  tomcat:
    threads:
      max: 400
    accept-count: 200
    max-connections: 10000

# Neo4j（示例，实际需用 Neo4j 官方 Spring Boot 或 Driver 配置）
spring:
  neo4j:
    uri: bolt://neo4j-host:7687
    authentication:
      username: neo4j
      password: ${NEO4J_PASSWORD}
    pool:
      max-connection-pool-size: 80
      connection-acquisition-timeout: 30s
```

### 3.4 图数据库层配置（Neo4j）

- **单机**：8C16G 及以上；Neo4j 堆内存 4～8G（`dbms.memory.heap.initial_size` / `max_size`）。
- **连接与线程池**：  
  `dbms.connector.bolt.thread_pool_min_size` / `thread_pool_max_size` 需 ≥ 所有应用实例的连接池总和（如 4×80=320，建议 400+）。
- **高可用**：1000 人场景可先单机；若需 99.9% 可用，再上因果集群（1 主 2 从）。

## 四、技术选型与依赖

### 4.1 图数据库选型

| 方案 | 说明 |
|------|------|
| **Neo4j**（推荐） | 成熟、Java 生态好、Cypher 表达力强，社区版可满足 1000 人；企业版支持集群与高级监控 |
| NebulaGraph | 国产、分布式能力强，适合超大规模图；若团队更熟悉 MySQL 生态可考虑 |
| 其他 | 如 JanusGraph + 后端存储，复杂度高，本方案不优先 |

### 4.2 后端依赖（示例）

```xml
<!-- Neo4j Java Driver -->
<dependency>
  <groupId>org.neo4j.driver</groupId>
  <artifactId>neo4j-java-driver</artifactId>
  <version>5.15.0</version>
</dependency>
```

- 移除：MySQL Connector、MyBatis（或仅保留少量非图数据场景）。
- 持久层：使用 Neo4j Driver 的 `Session`/`Transaction` 执行 Cypher，在 Service 层封装「节点/关系」的增删改查与分页。

### 4.3 可选：缓存与限流

- **Redis（可选）**：对热点查询（如组织树、当前用户菜单）做短 TTL 缓存，降低图库压力。
- **限流**：在 Nginx 或 Spring Boot（如 Resilience4j）对登录、列表等接口限流，防止突发流量打满图库。

## 五、部署与运维要点

### 5.1 部署方式

- **应用**：同一内网多台机器或 K8s 多副本，通过 Nginx/Ingress 做负载均衡；健康检查指向 `/api/actuator/health`（需在 Spring Boot 中启用）。
- **Neo4j**：单独部署；生产环境关闭默认的 7474 HTTP，仅开放 7687 Bolt，并配置防火墙与认证。
- **备份**：Neo4j 使用 `neo4j-admin database dump` 定期全量备份；必要时做 PITR（企业版）。

### 5.2 监控与容量观察

- **应用**：JVM 指标、Tomcat 线程池、请求 QPS/延迟（Prometheus + Grafana 或 Actuator + 日志）。
- **Neo4j**：连接数、查询耗时、锁等待；通过 Neo4j 自带监控或 Prometheus 插件采集。
- 当平均响应时间上升或连接数持续接近上限时，优先考虑：  
  - 优化 Cypher（索引、避免全图扫描）、  
  - 增加应用实例或 Neo4j 读副本。

## 六、与当前系统的差异与改造量

| 项目 | 当前（MySQL + MyBatis） | 本方案（仅图数据库） |
|------|--------------------------|----------------------|
| 数据存储 | 表 + 外键/关联表 | 节点 + 关系 |
| 查询语言 | SQL | Cypher（或图库等价物） |
| 持久层 | Mapper + XML | Neo4j Driver + Cypher / 封装层 |
| 事务 | MySQL 事务 | Neo4j 事务 |
| 分页/列表 | LIMIT/OFFSET | Cypher 的 SKIP/LIMIT + 总数查询 |

改造量：**大**。需重写所有与数据库交互的 Mapper/Service 逻辑，并设计数据迁移脚本（MySQL 导出 → 转成节点/关系并导入 Neo4j）。建议按模块分阶段迁移（先组织与权限，再项目与任务等）。

## 七、实施步骤建议

1. **选型与 POC**  
   确定图库产品（如 Neo4j），在测试环境部署；用当前系统核心实体（User、Company、Dept、Role、Project、Task）做小规模建模与 Cypher 查询验证。

2. **详细图模型与索引**  
   在 2.1～2.2 基础上细化属性与约束，在 Neo4j 中为高频查询字段建索引（如 `User.username`、`Project.id`、`Task.projectId`）。

3. **持久层替换**  
   引入 Neo4j Driver，按模块实现「图版」Repository/Service，保持现有 API 契约，便于前端无感切换。

4. **数据迁移**  
   编写脚本从 MySQL 读出数据，转换为节点与关系并写入 Neo4j；做一致性校验与回滚方案。

5. **性能与容量验证**  
   使用 JMeter/Gatling 等压测 200～500 req/s，观察应用与 Neo4j 的 CPU、内存、连接数及 P95 延迟；按需调大线程池、连接池或实例数。

6. **上线与灰度**  
   先灰度流量到「图库版」后端，验证无误后完全切到图数据库，下线 MySQL。

## 八、小结

- **可以只用图数据库**承载项目管理系统全部数据，并**通过应用水平扩展 + 图库连接与资源调优**支撑约 **1000 人同时在线**。
- 推荐以 **Neo4j** 为唯一数据源，Spring Boot 使用 Neo4j Driver 执行 Cypher，前端不变。
- 关键配置：**Tomcat 线程数 200～500/实例、Neo4j 连接池 50～100/实例、图库线程池 ≥ 总连接数、Neo4j 堆内存 4～8G**；实例数按压测结果取 2～4 个即可满足目标。
- 实施时需完成图模型设计、持久层重写、数据迁移与压测，建议分阶段进行。

若需要，可再针对某一模块（如组织树或任务依赖）给出更细的 Cypher 示例与索引建议。
